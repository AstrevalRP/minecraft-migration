# 1.21.11

> Changements constatés en migrant directement de 1.21.8 vers 1.21.11 (mappings **Yarn**). Certains ont pu apparaître dès 1.21.9 / 1.21.10.
> Déjà couverts par le blog Fabric, donc non repris ici : `Entity#getWorld` → `getEntityWorld`, `ResourceManagerHelper` → `ResourceLoader`, `GameRuleBuilder`.

## Gamerules — l'identifiant devient namespacé et en minuscules

### Problème / changement observé

Les gamerules sont maintenant enregistrées par `Identifier`. Un ancien nom en camelCase (`monModMaRegle`) n'est plus un chemin valide : il faut le renommer, ce qui change aussi la commande côté joueurs. Aucune migration n'est faite : une valeur personnalisée sur un monde existant est perdue.

```java
// Avant
public static final GameRules.Key<GameRules.IntRule> MA_REGLE =
    GameRuleRegistry.register(
        "monModMaRegle", GameRules.Category.UPDATES, GameRuleFactory.createIntRule(20, 1));
world.getGameRules().getInt(MA_REGLE);

// Après (net.minecraft.world.rule.*)
public static final GameRule<Integer> MA_REGLE =
    GameRuleBuilder.forInteger(20)
        .minValue(1)
        .category(GameRuleCategory.UPDATES)
        .buildAndRegister(Identifier.of(MOD_ID, "ma_regle"));
world.getGameRules().getValue(MA_REGLE);
```

> Penser à mettre à jour la doc et les tests qui exécutent `/gamerule monModMaRegle ...`. Dans les tests, construire la commande depuis l'identifiant plutôt que de dupliquer l'id du mod : `"gamerule " + MA_REGLE.getId() + " 1"`.

## Permissions — `hasPermissionLevel(int)` supprimé

### Problème / changement observé

`ServerCommandSource#hasPermissionLevel` et `PlayerEntity#hasPermissionLevel` n'existent plus. Les permissions passent par `PermissionPredicate` (`net.minecraft.command.permission`).

```java
// Avant
source.hasPermissionLevel(2);
player.hasPermissionLevel(2);

// Après
Permission gamemaster = new Permission.Level(PermissionLevel.GAMEMASTERS);
source.getPermissions().hasPermission(gamemaster);
player.getPermissions().hasPermission(gamemaster);
```

> `ServerCommandSource` implémente `PermissionSource`, mais **pas** `ServerPlayerEntity` (qui expose pourtant `getPermissions()`) : un helper typé `PermissionSource` ne peut pas recevoir un joueur.
> Pour un `.requires(...)` de commande : `PermissionChecks.requirePermissionLevel(PermissionChecks.GAMEMASTERS_CHECK)`.

## `World#isClient` — le champ devient privé

```java
// Avant
if (world.isClient) return;

// Après
if (world.isClient()) return;
```

## `UserCache` — remplacé par `NameToIdCache`

### Problème / changement observé

`MinecraftServer#getUserCache()` n'existe plus. Le cache nom → UUID est dans les `ApiServices` et renvoie des `PlayerConfigEntry` (record `id`, `name`) au lieu de `GameProfile`.

```java
// Avant
UserCache cache = server.getUserCache();
cache.findByName(name).map(GameProfile::getId);

// Après
NameToIdCache cache = server.getApiServices().nameToIdCache();
cache.findByName(name).map(PlayerConfigEntry::id);
```

## `PacketByteBuf` — `writeDate` / `readDate` supprimés

```java
// Avant
buf.writeDate(date);
Date date = buf.readDate();

// Après
buf.writeLong(date.getTime());
Date date = new Date(buf.readLong());
```

## `EntryListWidget.Entry#render` — nouvelle signature

### Problème / changement observé

Les lignes d'une liste connaissent maintenant leur propre position : `render` ne reçoit plus index, x, y, largeur, hauteur.

```java
// Avant
public void render(DrawContext context, int index, int y, int x, int entryWidth,
    int entryHeight, int mouseX, int mouseY, boolean hovered, float tickDelta) { ... }

// Après
public void render(DrawContext context, int mouseX, int mouseY, boolean hovered, float tickDelta) {
  int x = getContentX();
  int y = getContentY();
  int entryWidth = getContentWidth();
  ...
}
```

## Reload listeners — double enregistrement interdit

### Problème / changement observé

Enregistrer deux fois un reload listener avec le même identifiant lève désormais `Tried to register resource reloader <id> twice!` (ignoré silencieusement avant). Typiquement, un gametest qui rappelle la méthode d'init du mod échoue avec « Unknown internal error ».

> Ne pas rappeler l'enregistrement dans les tests : le mod l'a déjà fait au démarrage.
