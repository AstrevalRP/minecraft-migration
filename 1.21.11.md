# 1.21.11

> Changements constatés en migrant directement de 1.21.8 vers 1.21.11 (mappings **Yarn**). Certains ont pu apparaître dès 1.21.9 / 1.21.10.
> Déjà couverts par le blog Fabric, donc non repris ici : `Entity#getWorld` → `getEntityWorld`, `ResourceManagerHelper` → `ResourceLoader`, `GameRuleBuilder`.

## Yarn → Mojang — migration obligatoire avant 26.1

### Problème / changement observé

1.21.11 est la dernière version avec des mappings Yarn : à partir de 26.1, le jeu est livré non obfusqué et Fabric ne publie plus Yarn. Un mod en Yarn doit passer aux noms Mojang **en restant sur 1.21.11**, avant de toucher à la version de Minecraft. Procédure officielle : https://docs.fabricmc.net/1.21.11/develop/porting/mappings/loom (Loom ≥ 1.13).

```sh
# 1. Sources (src/main/java), sans toucher encore à gradle.properties ni build.gradle
./gradlew migrateMappings --mappings "net.minecraft:mappings:1.21.11" --overrideInputsIHaveABackup
# 2. Access widener / class tweaker, s'il y en a un
./gradlew migrateClassTweakerMappings --mappings "net.minecraft:mappings:1.21.11" --overrideInputsIHaveABackup
```

```groovy
// 3. build.gradle
// Avant
mappings "net.fabricmc:yarn:${project.yarn_mappings}:v2"
// Après
mappings loom.officialMojangMappings()
```

> Faire la migration des mappings dans une PR dédiée, séparée de l'upgrade de version : le renommage touche presque tous les fichiers et noierait les vrais changements d'API.
> `migrateMappings` ne traite que `src/main/java` par défaut. Les autres source sets se passent explicitement, sur place : `--input src/gametest/java --output src/gametest/java` (idem pour `src/client/java`, ou la tâche `migrateClientMappings` pour les split sources).
> Supprimer ensuite `yarn_mappings` de `gradle.properties`, puis relire les cibles de mixins (chaînes non remappées) et tout code par réflexion. Correspondances de noms : https://mappings.dev ou Linkie.
> Une fois en Mojang, les sections Yarn de ce knowledge base ne s'appliquent plus telles quelles : voir la section « Mappings Mojang » plus bas.

## Gamerules — l'identifiant devient namespacé et en minuscules

### Problème / changement observé

Les gamerules sont maintenant enregistrées par `Identifier`. Un ancien nom en camelCase (`monModMaRegle`) n'est plus un chemin valide : il faut le renommer, ce qui change aussi la commande côté joueurs. Aucune migration n'est faite : une valeur personnalisée sur un monde existant est perdue.

```java
// Avant
public static final GameRules.Key<GameRules.IntRule> MA_REGLE =
    GameRuleRegistry.register(
        "monModMaRegle", GameRules.Category.UPDATES, GameRuleFactory.createIntRule(20, 1));
world.getGameRules().getInt(MA_REGLE);

// Après (net.minecraft.world.rule.*)
public static final GameRule<Integer> MA_REGLE =
    GameRuleBuilder.forInteger(20)
        .minValue(1)
        .category(GameRuleCategory.UPDATES)
        .buildAndRegister(Identifier.of(MOD_ID, "ma_regle"));
world.getGameRules().getValue(MA_REGLE);
```

> Penser à mettre à jour la doc et les tests qui exécutent `/gamerule monModMaRegle ...`. Dans les tests, construire la commande depuis l'identifiant plutôt que de dupliquer l'id du mod : `"gamerule " + MA_REGLE.getId() + " 1"`.

## Permissions — `hasPermissionLevel(int)` supprimé

### Problème / changement observé

`ServerCommandSource#hasPermissionLevel` et `PlayerEntity#hasPermissionLevel` n'existent plus. Les permissions passent par `PermissionPredicate` (`net.minecraft.command.permission`).

```java
// Avant
source.hasPermissionLevel(2);
player.hasPermissionLevel(2);

// Après
Permission gamemaster = new Permission.Level(PermissionLevel.GAMEMASTERS);
source.getPermissions().hasPermission(gamemaster);
player.getPermissions().hasPermission(gamemaster);
```

> `ServerCommandSource` implémente `PermissionSource`, mais **pas** `ServerPlayerEntity` (qui expose pourtant `getPermissions()`) : un helper typé `PermissionSource` ne peut pas recevoir un joueur.
> Pour un `.requires(...)` de commande : `CommandManager.requirePermissionLevel(CommandManager.GAMEMASTERS_CHECK)` (`net.minecraft.server.command.CommandManager`, et non `PermissionChecks`).

## `World#isClient` — le champ devient privé

```java
// Avant
if (world.isClient) return;

// Après
if (world.isClient()) return;
```

## `UserCache` — remplacé par `NameToIdCache`

### Problème / changement observé

`MinecraftServer#getUserCache()` n'existe plus. Le cache nom → UUID est dans les `ApiServices` et renvoie des `PlayerConfigEntry` (record `id`, `name`) au lieu de `GameProfile`.

```java
// Avant
UserCache cache = server.getUserCache();
cache.findByName(name).map(GameProfile::getId);

// Après
NameToIdCache cache = server.getApiServices().nameToIdCache();
cache.findByName(name).map(PlayerConfigEntry::id);
```

## `PacketByteBuf` — `writeDate` / `readDate` supprimés

```java
// Avant
buf.writeDate(date);
Date date = buf.readDate();

// Après
buf.writeLong(date.getTime());
Date date = new Date(buf.readLong());
```

## `EntryListWidget.Entry#render` — nouvelle signature

### Problème / changement observé

Les lignes d'une liste connaissent maintenant leur propre position : `render` ne reçoit plus index, x, y, largeur, hauteur.

```java
// Avant
public void render(DrawContext context, int index, int y, int x, int entryWidth,
    int entryHeight, int mouseX, int mouseY, boolean hovered, float tickDelta) { ... }

// Après
public void render(DrawContext context, int mouseX, int mouseY, boolean hovered, float tickDelta) {
  int x = getContentX();
  int y = getContentY();
  int entryWidth = getContentWidth();
  ...
}
```

## Reload listeners — double enregistrement interdit

### Problème / changement observé

Enregistrer deux fois un reload listener avec le même identifiant lève désormais `Tried to register resource reloader <id> twice!` (ignoré silencieusement avant). Typiquement, un gametest qui rappelle la méthode d'init du mod échoue avec « Unknown internal error ».

> Ne pas rappeler l'enregistrement dans les tests : le mod l'a déjà fait au démarrage.

## GameProfile — devient un record

### Problème / changement observé

La version d'authlib livrée avec 1.21.11 fait de `com.mojang.authlib.GameProfile` un record : `getId()` et `getName()` n'existent plus.

```java
// Avant
profile.getId();
profile.getName();

// Après
profile.id();
profile.name();
```

> `NameToIdCache` renvoie des `PlayerConfigEntry` ; pour garder une API en `GameProfile` : `new GameProfile(entry.id(), entry.name())`. L'exemple `GameProfile::getId` de la section `UserCache` concerne l'ancien code.

## BlockEntityRenderer — passage aux render states

### Problème / changement observé

`BlockEntityRenderer<T>` devient `BlockEntityRenderer<T, S extends BlockEntityRenderState>`. On lit les données dans `updateRenderState`, puis on dessine dans `render`. `ItemRenderer#renderItem` passe par `ItemRenderState`.

```java
// Avant
public void render(T entity, float tickDelta, MatrixStack m, VertexConsumerProvider v, int light, int overlay, Vec3d cam) {
  itemRenderer.renderItem(stack, ctx, light, OverlayTexture.DEFAULT_UV, m, v, world, 1);
}

// Après
public S createRenderState() { return new S(); }
public void updateRenderState(T entity, S state, float tickDelta, Vec3d cam, @Nullable CrumblingOverlayCommand crumbling) {
  BlockEntityRenderer.super.updateRenderState(entity, state, tickDelta, cam, crumbling);
  itemModelManager.clearAndUpdate(state.item, stack, ctx, entity.getWorld(), null, 1); // context.itemModelManager()
}
public void render(S state, MatrixStack m, OrderedRenderCommandQueue queue, CameraRenderState camera) {
  state.item.render(m, queue, state.lightmapCoordinates, OverlayTexture.DEFAULT_UV, 0);
}
```

> `state.lightmapCoordinates` et `state.blockState` sont remplis par l'implémentation par défaut de `updateRenderState`.

## `AbstractBlock#getComparatorOutput` — paramètre `Direction` ajouté

```java
// Avant
protected int getComparatorOutput(BlockState state, World world, BlockPos pos)

// Après
protected int getComparatorOutput(BlockState state, World world, BlockPos pos, Direction direction)
```

## Mappings Mojang (officiel) — écarts supplémentaires

> Section issue de la migration de **astreval-locks** (1.21.8 → 1.21.11, mappings Mojang).

### `ResourceKey#location()` → `identifier()`

```java
// Avant
key.location().getNamespace()

// Après
key.identifier().getNamespace()
```

### `CustomData#contains(String)` supprimé

La surcharge `contains(String)` n'existe plus sur `CustomData`. Passer par `copyTag()` pour récupérer un `CompoundTag` interrogeable.

```java
// Avant
stack.get(DataComponents.CUSTOM_DATA).contains(KEY)

// Après
stack.get(DataComponents.CUSTOM_DATA).copyTag().contains(KEY)
```

### `Camera#getPosition()` → `Camera#position()`

```java
// Avant
camera.getPosition()

// Après
camera.position()
```

### `Player.oBob` / `Player.bob` supprimés → `LocalPlayer.yBobO` / `LocalPlayer.yBob`

Les champs de balancement de vue ont migré de `Player` (obfusqué) vers `LocalPlayer` avec des noms Mojang différents. Vérifier avec `instanceof LocalPlayer` avant accès.

```java
// Avant
float f1 = -player.oBob;
float f2 = Mth.lerp(partialTicks, player.oBob, player.bob);

// Après
if (mc.getCameraEntity() instanceof LocalPlayer localPlayer) {
    float f1 = -localPlayer.walkAnimation.position(partialTicks);
    float f2 = Mth.lerp(partialTicks, localPlayer.yBobO, localPlayer.yBob);
}
```

### `RenderType.LINES` déplacé vers `RenderTypes.LINES`

La constante statique a migré dans une nouvelle classe.

```java
// Avant
import net.minecraft.client.renderer.RenderType;
RenderType.LINES

// Après
import net.minecraft.client.renderer.rendertype.RenderTypes;
RenderTypes.LINES
```

### `LevelRenderer.cullingFrustum` supprimé — `capturedFrustum` seul subsiste

```java
// Avant
Frustum f = levelRenderer.cullingFrustum;

// Après
Frustum f = levelRenderer.capturedFrustum; // null si pas de frustum capturé
```

> À retirer aussi de l'access widener si présent (`accessible field net/minecraft/client/renderer/LevelRenderer cullingFrustum ...`).

### `ItemRenderer#renderStatic` supprimé — rendu via `ItemStackRenderState`

La chaîne de rendu item passe désormais par un objet d'état intermédiaire, et soumet dans un `SubmitNodeCollector` (appelé `cmdQueue` dans `WorldRenderContext#commandQueue()`).

```java
// Avant
mc.getItemRenderer().renderStatic(stack, ItemDisplayContext.FIXED,
    light, OverlayTexture.NO_OVERLAY, poseStack, buffer, mc.level, seed);

// Après
ItemStackRenderState renderState = new ItemStackRenderState();
mc.getItemModelResolver().updateForNonLiving(renderState, stack, ItemDisplayContext.FIXED, null);
renderState.submit(poseStack, cmdQueue, light, OverlayTexture.NO_OVERLAY, 0);
```

### `ShapeRenderer#renderLineBox` supprimé → `ShapeRenderer#renderShape`

```java
// Avant
ShapeRenderer.renderLineBox(poseStack, vertexConsumer, minX, minY, minZ, maxX, maxY, maxZ, r, g, b, a);

// Après
VoxelShape shape = Shapes.box(minX, minY, minZ, maxX, maxY, maxZ);
ShapeRenderer.renderShape(poseStack, vertexConsumer, shape, 0d, 0d, 0d, argbColor, alpha);
```

### `Screen#keyPressed(int,int,int)` / `keyReleased` → `KeyEvent`

La signature des callbacks clavier change : les trois `int` (key, scancode, modifiers) deviennent un record `KeyEvent`.

```java
// Avant
@Override
public boolean keyPressed(int key, int scancode, int modifiers) { ... }

// Après
@Override
public boolean keyPressed(net.minecraft.client.input.KeyEvent event) {
    int key = event.key();
    int scancode = event.scancode();
    int modifiers = event.modifiers();
    ...
}
```

### `ChestBlock#candidatePartnerFacing` — signature modifiée

```java
// Avant (mixin)
@Inject(method = "candidatePartnerFacing")
private void candidatePartnerFacing(BlockPlaceContext ctx, Direction dir, CallbackInfoReturnable<Direction> cir)

// Après
@Inject(method = "candidatePartnerFacing")
private void candidatePartnerFacing(Level world, BlockPos pos, Direction dir, CallbackInfoReturnable<Direction> cir)
```

### `WorldRendererMixin` — cible cassée par un nouveau paramètre `Matrix4f`

Le mixin ciblant `renderLevel` (ou équivalent renommé en 1.21.11) ne s'applique plus : la méthode a reçu un paramètre `Matrix4f` supplémentaire. Remplacer par l'événement Fabric API `WorldRenderEvents.END_MAIN`.

```java
// LocksClient.onInitializeClient()
WorldRenderEvents.END_MAIN.register(context -> {
    float pt = Minecraft.getInstance().getDeltaTracker().getGameTimeDeltaPartialTick(true);
    renderLocks(context.matrices(), context.commandQueue(),
        levelRenderer.capturedFrustum, pt);
});
```

> Le package correct en 1.21.11 est `net.fabricmc.fabric.api.client.rendering.v1.world.WorldRenderEvents` (sous-package `.world` ajouté).
> `WorldRenderContext` expose : `commandQueue()` (`SubmitNodeCollector`), `matrices()` (`PoseStack`), `consumers()` (`MultiBufferSource`), `worldRenderer()` (`LevelRenderer`), `gameRenderer()`. Il n'a **pas** de `projectionMatrix()`.

### Access widener — auditer les classes/champs supprimés

Les entrées suivantes lèvent `access-widener validation failed` en 1.21.11 :

- `LevelRenderer.cullingFrustum` (champ supprimé)
- `VillagerTrades$ItemsForEmeralds` (classe supprimée/renommée)
- `VillagerTrades$EnchantedItemForEmeralds` (classe supprimée/renommée)
